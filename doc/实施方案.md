> **C2C Protocol 是 Avalanche 上第一个 Agent Reputation Infrastructure Protocol。**

## 1. Avalanche Native Advantage（为什么必须是 Avalanche）

评审必问："换成 Ethereum/Base/Polygon，方案是否仍然成立？"
本节证明：**C2C 的协议形态由 Avalanche 的基础设施能力直接塑造，迁移成本高、原生收益大。**

| Avalanche 能力 | C2C 使用场景 | 不可替代价值 |
| --- | --- | --- |
| **C-Chain（亚秒终局 + 低 gas）** | Reputation 是**高频写入**数据：每个 Agent 每次任务完成都可能触发 score 更新与 proof 锚定 | 在 L1 主网做同样频率的状态更新成本不可行；C-Chain 让"每次协作都上链"在经济上成立 |
| **@avalanche-sdk/client（TS SDK）** | Agent SDK 的链交互底座：账户派生、C-Chain 读写、事件监听，与 Agent 开发者主流的 TS 技术栈零摩擦 | Agent 生态在 TS/Node 侧，Avalanche 提供原生 TS SDK 而非社区封装，接入成本最低 |
| **Glacier Data API** | Reputation 查询、Passport 持有验证、历史事件检索 | **不需要自建 indexer**——协议从第一天就有生产级数据层，小团队也能支撑开放查询 API |
| **Webhook API** | `ScoreUpdated` 事件 → 实时推送 → Agent 立即获知声誉变化 | Agent Economy 需要**实时反馈回路**（Agent 根据声誉动态调整报价/接单策略），轮询架构做不到产品级体验 |
| **Metrics API** | Demo 与运营侧展示协议真实链上活跃度 | Retro9000 以 gas burn 排名，Metrics API 是协议增长的官方度量口径 |
| **未来 Avalanche L1 + ICM/Teleporter** | Phase 4：Credit Chain——独立 Agent 经济层，声誉状态跨 L1 同步 | 声誉结算层最终需要自己的执行环境（自定义 gas 代币、免 gas 评分更新）；只有 Avalanche 提供从 C-Chain 合约到自有 L1 的平滑演进路径 |

**一句话论证：**

> C2C 是高频写入 + 实时反馈 + 终局需自有执行环境的 Reputation Settlement 协议。
> 这三个需求分别对应 Avalanche 的 C-Chain 性能、Webhook/Glacier 实时数据层、L1 演进路径——
> 三者同时在单一生态内成立的，只有 Avalanche。

## 4. Reputation 模型：从单一分数到 Reputation Vector

**问题**：单一 Score 像 Web2 信用分，不像协议。Agent 的能力是多维的——
" coding 强但响应慢"与"全能平庸"应得到不同声誉画像，且与 Dashboard 雷达图 UI 直接对应。

### 4.1 Reputation Vector

```json
{
  "execution": 820,
  "reliability": 910,
  "quality": 760,
  "collaboration": 880
}
```

| 维度 | 权重 | 含义 | 数据来源 |
| --- | --- | --- | --- |
| Execution | 30% | 任务完成能力（完成率、复杂度加权） | 任务事件 |
| Reliability | 30% | 稳定可靠性（历史成功率的时序衰减加权） | 成功/失败事件流 |
| Quality | 25% | 产出质量（AI 评估 + 人工反馈） | 评估结果 |
| Collaboration | 15% | 协作表现（响应速度、沟通、多方评价） | 交互事件 |

### 4.2 综合分

```
Score = Execution×30% + Reliability×30% + Quality×25% + Collaboration×15%   (0–10000)
Level：Bronze 3000 / Silver 5000 / Gold 7000 / Platinum 8500 / Diamond 9000+
```

### 4.3 协议化价值

- **Vector 上链**：四个维度分别锚定，第三方应用可按自己的权重重算综合分（协议可组合性）。
- **雷达图直出**：前端 Dashboard 雷达图四个轴 = 链上四个维度，UI 与协议模型 1:1。
- **可演进**：未来新增维度不改合约结构（vector 以 bytes32 编码槽位扩展）。

## 5. Agent SDK：核心产品设计（协议的采用入口）

> SDK 不是辅助工具，**SDK 就是产品本身**。评审理解 C2C 的第一扇窗。
> **第一设计原则：agent-agnostic。** Agent 可以是任何 Agent——DeepSeekCode、Claude Code、
> Codex CLI、LangChain、AutoGen、企业自研系统，甚至一个 cron 脚本。协议只关心"签名事件"，
> 不关心事件由谁、用什么框架产生。

### 5.1 分层接入模型（任何 Agent 都能接入）

| 层级 | 接入方式 | 适用对象 | 接入成本 |
| --- | --- | --- | --- |
| **L0 开放协议** | HTTP + 签名事件信封（不依赖 SDK，任何语言） | 任何 Agent / 脚本 / 后端服务 | 一个 POST 请求 |
| **L1 核心 SDK** | `@c2c/agent-sdk` 核心包，**零框架依赖**，纯协议客户端 | 任何 TS/Node Agent（DeepSeekCode、自研 Agent 等） | 几行代码 |
| **L2 生命周期适配器** | 实现统一 `AgentHarness` 接口的适配器，自动把宿主 Agent 的任务生命周期翻译成 C2C 事件 | CLI 类 Agent（DeepSeekCode / Claude Code / Codex CLI）、框架类（LangChain / AutoGen） | 一行配置 |

```
┌─ L2 适配器层 ─────────────────────────────────────┐
│ @c2c/adapter-deepseekcode  (DeepSeekCode 插件)     │
│ @c2c/adapter-claude-code   (hooks 配置)            │
│ @c2c/adapter-codex         (notify/hook 配置)      │
│ @c2c/adapter-langchain     (callback handler)      │
│ @c2c/adapter-autogen       (hook 注入)             │
│ ... 社区可贡献任意适配器                             │
└──────────────┬─────────────────────────────────────┘
               │ 统一 AgentHarness 接口
┌──────────────▼─────────────────────────────────────┐
│ L1 @c2c/agent-sdk 核心（零框架依赖）                  │
│ initialize / task.start / task.complete /          │
│ proof.submit / reputation.get                      │
└──────────────┬─────────────────────────────────────┘
               │ 签名事件信封（EIP-191 签名 + 幂等键）
┌──────────────▼─────────────────────────────────────┐
│ L0 C2C Event API（POST /events，协议规范公开）        │
└────────────────────────────────────────────────────┘
```

### 5.2 L0：开放事件协议（不定死任何 Agent 的根本保证）

事件信封规范公开，任何语言的 Agent 都可直接对接：

```json
POST /events
{
  "eventId": "evt_uuid",              // 幂等键
  "agentId": "agent_001",
  "agentFramework": "deepseekcode",   // 自由文本：deepseekcode / claude-code / codex / langchain / custom...
  "action": "task.completed",         // task.started | task.completed | task.failed | proof.submitted
  "taskId": "task_123",
  "payload": { "resultURI": "ipfs://...", "durationMs": 42000, "qualitySelfReport": 0.92 },
  "timestamp": 1757xxxxxx,
  "signature": "0x..."                // Agent 身份密钥对 canonical payload 的 EIP-191 签名
}
```

`agentFramework` 只是**元数据标签**（用于生态统计与声誉画像细分），协议逻辑对它零依赖——
这是"不能定死"在协议层的落实。

### 5.3 L1：核心 SDK（零框架依赖）

```typescript
import { C2CAgent } from "@c2c/agent-sdk";

const agent = new C2CAgent({
  apiKey: "c2c_xxx",
  endpoint: "https://api.c2c.network",
  agentId: "agent_001",
});

// 初始化：校验身份、拉取链上声誉快照（走 Glacier Data API）
await agent.initialize();
// → { passport: true, vector: {...}, level: "Gold", snowtraceURL: "..." }

// 任务生命周期 = 声誉事件流（手动埋点，适合自研 Agent）
const task = await agent.task.start({ taskId: "task_123", type: "code_review" });
await agent.task.complete(task, { resultURI: "ipfs://bafy...", qualitySelfReport: 0.92 });

await agent.proof.submit({ taskId: "task_123", proofCID: "bafy..." });

// 查询自己/他人声誉
const rep = await agent.reputation.get("agent_002");
// → { vector: {...}, score: 8750, level: "Platinum", proofHash, chainVerified: true }
```

- **幂等与降级**：eventId 幂等键；API 不可达时本地队列缓存 + 指数退避重试，Agent 主流程永不阻塞。
- **运行时兼容**：纯 fetch + 可选 viem，Node / Bun / Deno / 浏览器均可运行（DeepSeekCode 是 Bun 技术栈，核心包不得引入 Node-only 依赖）。
- **链交互底座**：`@avalanche-sdk/client`；链配置从 `viem/chains` 导入
  （**勿用 `@avalanche-sdk/client/chains`，ekta re-export 是坏的**，见 ENVIRONMENT.md §7-5）。

### 5.4 L2：统一适配器接口 AgentHarness

所有适配器实现同一个接口，把"任意 Agent 的生命周期"映射为"C2C 事件流"：

```typescript
interface AgentHarness {
  readonly name: string;  // "deepseekcode" | "claude-code" | "codex" | ...
  onSessionStart?(ctx: SessionContext): void | Promise<void>;
  onTaskStart?(ctx: TaskContext): void | Promise<void>;
  onTaskComplete?(ctx: TaskContext, result: TaskResult): void | Promise<void>;
  onTaskFailed?(ctx: TaskContext, error: unknown): void | Promise<void>;
}
```

内置适配器（V1 交付前三个，评审演示用）：

| 适配器 | 接入机制 | 说明 |
| --- | --- | --- |
| `@c2c/adapter-deepseekcode` | **DeepSeekCode 插件**（订阅宿主全量事件流，机制同官方 trajectory 插件） | **首个 dogfood 参考实现**：DeepSeekCode 执行任务时自动产生 C2C 声誉事件，零侵入 |
| `@c2c/adapter-claude-code` | Claude Code hooks（PreToolUse / Stop 等生命周期钩子 → 调核心 SDK） | 配置文件级接入，不改 Claude Code 本体 |
| `@c2c/adapter-codex` | Codex CLI notify/hook 配置 → 调核心 SDK | 同上 |
| `@c2c/adapter-langchain` | LangChain callback handler 自动埋点 | 框架类代表（V1 可选） |
| `@c2c/adapter-autogen` | AutoGen hook 注入 | 框架类代表（V1 可选） |

> **dogfood 策略**：DeepSeekCode（`C:\Users\HUAWEI\Desktop\deepseekcode`，Bun + 插件体系）作为
> C2C 的第一个真实接入方。其插件机制（参考 `packages/plugins/trajectory`：订阅宿主事件流 +
> append-only 日志）与 C2C 事件上报天然同构——适配器几乎只是"把事件流转发给 C2C API"。
> Demo 中可直接展示"一个真实 coding agent 在工作中积累链上声誉"，这是最有说服力的评审素材。

### 5.5 Agent 注册与框架无关性

Agent 注册时的 metadata 声明框架信息，但协议不校验、不限制：

```json
{
  "name": "DeepSeekCode-Agent-01",
  "framework": "deepseekcode",     // 任意字符串，仅作画像标签
  "capabilities": ["coding", "code_review"],
  "operator": "0x123..."
}
```

新增一类 Agent = 新增一个适配器（或直接用 L0/L1），**协议、合约、后端零改动**。

### 6.1 信任机制：EIP-712 Attestation Signature（V2.0 新增）

**回应评审追问"为什么相信你的 backend"**：后端不是"有权限直接改分"，
而是"签发可验证的评估声明"，合约只做密码学验证——信任根是签名密钥，不是 API 服务器。

```
Agent Event → Backend 计算 Vector → 构造 Attestation → Signer 私钥签名
→ 任何人（用户/SDK/后端）携带签名调合约 → 合约 ecrecover 验证 → 更新状态
```

```solidity
// EIP-712 typed data
struct ScoreAttestation {
    uint256 agentId;
    uint32 execution;      // 0-10000
    uint32 reliability;
    uint32 quality;
    uint32 collaboration;
    uint256 tasksCompleted;
    bytes32 proofHash;     // keccak256(IPFS proof JSON)
    uint256 nonce;         // per-agent 防重放
    uint64  deadline;
}

function submitScore(ScoreAttestation calldata att, bytes calldata sig) external {
    require(block.timestamp <= att.deadline, "expired");
    require(att.nonce == nonces[att.agentId]++, "bad nonce");
    address signer = _hashTypedData(att).recover(sig);
    require(hasRole(EVALUATOR_ROLE, signer), "bad evaluator");
    _applyScore(att);
    emit ScoreUpdated(att.agentId, compositeOf(att), att.proofHash);
}
```

**收益**：
- API 服务器被拖库 ≠ 声誉被篡改（签名密钥独立保管，可放 HSM/KMS）。
- 天然支持未来多评估者：`EVALUATOR_ROLE` 授予多个独立 attester → V2 平滑演进为 attester 网络。
- 用户可自助上链：后端只负责签名，gas 可由用户支付（去中心化叙事）。

### 6.6 TaskRegistry.sol（任务登记，Sprint 1 新增）

链下任务状态机（Open → Assigned → Completed）的**链上审计登记层**：只登记「谁发布 / 谁领取 / 何时完成」，
不做支付/竞价/撮合（守 V1 红线）。声誉门槛在链下读取 `ReputationRegistry.compositeScore` 校验通过后才调用 assignTask——链上不裁决分数。

```solidity
struct TaskRecord {
    bytes32 taskHash;      // keccak(chainId, publisher, externalId, minScore) —— 服务端可重算
    address publisher;     // 发布者
    uint256 minScore;      // 声誉门槛 0–10000（链下校验）
    uint256 agentId;       // 领取 Agent（未领取 = 0）
    bool assigned; bool completed;
    uint64 createdAt; uint64 assignedAt; uint64 completedAt;
}
function publishTask(bytes32 taskHash, uint256 minScore, uint64 deadline) external; // → TaskPublished
function assignTask(bytes32 taskHash, uint256 agentId) external;                    // → TaskAssigned（仅一次）
function completeTask(bytes32 taskHash) external;                                   // only publisher → TaskCompleted
```

- API 层：`POST /tasks`（发布上链）→ `POST /tasks/:externalId/claim`（校验门槛 + assign 上链）→
  SDK `task.completed`（taskId=externalId）事件对账置 Completed；`GET /tasks` 市场列表。
- Web：Dashboard 底部 Task Marketplace 面板（发布表单 + OPEN 列表 + 领取，Demo 私钥直连水印）。

| event | SDK 事件入口：签名校验、幂等去重、时间戳单调性 |
| reputation | Vector 引擎（`@c2c/reputation-engine` 纯函数包，可单测）：时序衰减、任务复杂度加权 |
| attestation | 构造 ScoreAttestation → Signer（KMS/环境密钥）EIP-712 签名 → 返回给调用方上链 |
| proof | 生成 proof JSON（含 vector、事件摘要、评估依据）→ Pinata 上传 → CID/hash |
| indexer | Webhook 接收 `ScoreUpdated`（降级方案：Glacier Data API 轮询）→ 更新读模型缓存 |

**端到端数据流（Path 2 全貌）：**

```
Agent Runtime (SDK) → POST /events → Engine 计算 Vector
→ 生成 proof JSON → Pinata IPFS → EIP-712 签名
→ submitScore(att, sig) 上链（Fuji）→ Snowtrace 可查
→ Webhook 回推 → Dashboard/雷达图实时更新
```

**Prisma 核心表**：`User(walletAddress)` `Agent(id, ownerId, chainAgentId, metadataURI)`
`Event(id, agentId, idempotencyKey, action, payload)` `VectorSnapshot(agentId, execution, reliability, quality, collaboration, proofHash, createdAt)`
`Proof(hash, cid, agentId, payloadJson)`

**反作弊 V1 底线**：事件幂等、评分更新频率限制、单 Agent 异常波动告警（人工 review 队列）。

## 9. Why C2C Wins（竞争壁垒）

### 9.1 Reputation Graph（网络效应壁垒）

不是孤立 Agent 分数，而是可信关系网络：

```
Agent ←task→ Human
  ↕ collab      ↕ endorsement
Agent ←attestation→ Organization
```

每条边都是签名事件——后来者无法靠刷分复制一个真实协作图谱。

### 9.2 Portable Reputation（资产壁垒）

Passport NFT + 链上 Vector = 用户拥有的声誉资产，可跨应用/跨平台验证，
直接击穿"Upwork 评分无法迁移"的行业痛点。

### 9.3 Open SDK Adoption（生态壁垒）

**Agent-agnostic**：任何 Agent——DeepSeekCode、Claude Code、Codex、LangChain、AutoGen、
自研系统——都能接入：协议层（L0）一个 POST 请求，核心 SDK（L1）几行代码，适配器（L2）一行配置。
SDK 每多一个集成方，协议的声誉数据网络就厚一层——**采用即壁垒**。

## 13. 风险与对策

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| Snowtrace verify 失效 | 中 | 先实测；降级 README 公示源码+tx（ENVIRONMENT.md §9） |
| Signer 密钥泄露 | 中 | EIP-712 架构下密钥独立于 API 服务器，放 KMS；泄露后 revoke EVALUATOR_ROLE 换钥即可，历史 attestation 不受影响 |
| 评分算法被质疑中心化 | 中 | Vector 与 proof 全量上链可查，第三方可重算；V2 attester 网络路线已预留 |
| IPFS 可用性 | 低 | Pinata 固定 + proof JSON 落库，CID 可重算 |
| 公共 RPC 限流 | 低 | 已知坑容错；必要时 AvaCloud 付费 RPC |
| pnpm 12 构建脚本拦截 | 低 | 各子工程 pnpm-workspace.yaml 维护 allowBuilds |
| 范围蔓延 | 高 | 三条核心路径为唯一验收标准，其余皆 mock 或禁止 |
